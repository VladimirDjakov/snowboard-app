# Runbook и эксплуатация

В этом документе собраны советы по эксплуатации системы, диагностике проблем и воспроизводимости обработки. Он предназначен для разработчиков и DevOps‑инженеров.

## Запуск в development

1. **Настройте окружение.** Скопируйте пример переменных окружения и заполните необходимое:

   ```bash
   cp .env.example .env
   # при необходимости скорректируйте DATABASE_URL, REDIS_URL, TRITON_URL
   # По умолчанию используется локальная ФС (STORAGE_BACKEND=local)
   # Для S3/MinIO установите STORAGE_BACKEND=s3 и настройте S3_* переменные
   ```

2. **Поднимите сервисы.** Используйте docker compose:

   ```bash
   make dev-up
   ```

   Это запустит Postgres, Redis, Triton (GPU), API, CPU‑воркер, GPU‑воркер. MinIO не запускается по умолчанию (опционален, только для S3 storage backend). Проверьте, что контейнеры корректно стартовали (`docker compose ps`).

3. **Загрузите модель для Triton.** Выполните:

   ```bash
   make pull-models
   ```

   Скрипт скачает архив модели из указанного artifact store, проверит контрольную сумму и распакует в `runtime/triton_model_repository`. Если модель не скачивается или sha256 не сходится, проверьте сетевое соединение и актуальность версии.

4. **Выполните миграции базы данных.**

   ```bash
   make migrate
   ```

5. **Откройте фронтенд.** Перейдите в браузере на `http://localhost:3000` (если фронтенд запускается отдельно) или на `http://localhost` (если фронтенд обслуживается API).

## Миграции в production

Для применения миграций в production окружении см. подробное руководство: [Database Guide](./database.md)

**Краткая версия:**
- Миграции выполняются **ДО** запуска нового кода
- Миграции выполняются через CI/CD pipeline как отдельный шаг
- Всегда делайте бэкап перед миграциями
- Тестируйте миграции на staging перед production

## Мониторинг и логирование

### Логи

Все сервисы пишут структурированные логи в stdout. Их можно просматривать командой:

```bash
docker compose logs -f api
docker compose logs -f worker-cpu
docker compose logs -f worker-gpu
docker compose logs -f triton
```

В логах воркеров включены поля `video_id`, `stage`, `latency_ms`, что помогает быстро находить проблемы. Для production рекомендовано настроить сбор логов в систему централизованного логирования (например, Loki/Grafana или Elasticsearch).

### Метрики

Для наблюдения за системой следует настроить Prometheus и Grafana (не входит в MVP). Минимальный набор метрик:

- `jobs_in_queue{stage}` — длина очереди по стадиям.
- `job_latency_seconds{stage}` — время выполнения задач.
- `gpu_infer_latency_seconds` — время инференса модели.
- `failed_jobs_total` — количество неуспешных задач.

Пороговые алерты: рост очереди GPU, длительная задержка инференса, увеличение числа ошибок.

## Частые проблемы и решения

### Triton не стартует

- Убедитесь, что каталог `runtime/triton_model_repository` содержит корректную структуру: папку модели (`pose_model`) с файлом `config.pbtxt` и подкаталогом версии (`1/`), в котором лежит `model.plan`. Проверьте права доступа.
- Проверьте переменную `TRITON_URL` в `.env` и указание GPU (см. `device-gpu` в docker compose). Если GPU недоступен, Triton может не запуститься.

### Очередь растёт

- Посмотрите длину очереди (Redis key `rq:queue:gpu` / `rq:queue:cpu`). Если количество задач растёт, увеличьте количество соответствующих воркеров (`scale` в docker compose) или уменьшите размер загружаемых видео.
- Убедитесь, что GPU‑воркеры не блокируются. Просмотрите логи: проблемы могут быть в модели (несоответствие контракта) или в данных (коррупция видео).

### Нет GPU

- Для разработки можно запускать инференс на CPU, но время обработки значительно увеличится. Проверьте, доступна ли CUDA (`nvidia-smi`) и корректно ли смонтирован драйвер в контейнеры.
- Для продакшена необходимо предусмотреть fallback: не принимать видео, если нет доступных GPU; уведомлять пользователя о задержке.

### Плеер не отображает позу

- Проверьте, что фронтенд получил файлы keypoints и загрузил их. В консоли браузера не должно быть ошибок при fetch.
- Убедитесь, что временные отметки `ts` в `keypoints.jsonl` соответствуют нормализованному видео (FPS, длительность). Если рассинхронизация велика, убедитесь в правильном вычислении `ts` при транскодинге и инференсе.

## Воспроизводимость обработки

Для воспроизводимости результатов храните версии конвейера и артефактов. В таблице `videos` есть поля `pipeline_version`, `model_version`, `features_version`, `ruleset_version`. При изменении модели, правил или схемы фич увеличивайте соответствующий номер версии. Для повторной обработки определённого видео используйте тот же набор версий. Идемпотентность задач и проверка существования артефактов позволяют безопасно запускать обработку повторно.

## Storage Backends

Система поддерживает два типа storage backends:

### Локальная файловая система (по умолчанию для MVP)

- **Настройка:** `STORAGE_BACKEND=local` в `.env`
- **Преимущества:** Простота, нет дополнительных сервисов, высокая производительность
- **Расположение файлов:** `runtime/storage/raw/` и `runtime/storage/proc/`
- **Доступ:** Через API endpoints `/api/v1/files/{key}`

### S3/MinIO (для продакшена)

- **Настройка:** `STORAGE_BACKEND=s3` в `.env` и настройка S3_* переменных
- **Запуск MinIO:** Раскомментируйте секцию `minio` в `docker-compose.yml`
- **Преимущества:** Масштабируемость, репликация, presigned URLs
- **Доступ:** Через presigned URLs, генерируемые storage backend

### Переключение между backends

1. Измените `STORAGE_BACKEND` в `.env` (`local` или `s3`)
2. Если используете S3, настройте S3_* переменные и раскомментируйте MinIO в docker-compose.yml
3. Перезапустите сервисы: `make dev-up`

Код остаётся без изменений благодаря абстракции storage backend.

## Проверка здоровья и готовности

В backend можно реализовать эндпоинт `/health/ready`, который проверяет:

- доступность базы данных;
- наличие модели в `triton_model_repository`;
- способность API выполнить простой запрос к очереди Redis;
- доступность object storage.

Этот эндпоинт может использоваться оркестратором (Docker Compose, Kubernetes) для контроля состояния.

## Масштабирование и продакшен

На этапе MVP достаточно docker compose. Для продакшена рекомендуется:

1. **Использовать управляемые сервисы.** СУБД (RDS/CloudSQL), очередь сообщений (RabbitMQ, Kafka), object storage (S3/GCS), GPU воркеры на выделенных машинах.
2. **Оркестрация воркеров.** Перейти от Redis + RQ к более устойчивым системам (Celery/RabbitMQ, Argo Workflows, Temporal) для управления зависимостями и ретраями.
3. **Мониторинг.** Настроить мониторинг инфраструктуры и приложения (Prometheus, Grafana, Loki). Автоматические алерты по метрикам, логам и состоянию очереди.
