# Форматы данных

В этом документе описываются форматы файлов, которые производятся и потребляются в ходе работы системы. Поддержка версионирования позволяет изменить схему, не нарушая совместимость с существующими артефактами.

## 1. Ключевые точки — `keypoints_v1.jsonl`

Каждый кадр видео записывается отдельной строкой в формате JSONL (JSON Lines). Такой подход позволяет писать файл стримингом и восстанавливать прогресс при сбоях.

### Структура строки

```json
{
  "frame": 123,
  "ts": 4.10,
  "person_id": 0,
  "kp": [
    { "name": "LHip", "x": 0.52, "y": 0.63, "c": 0.91 },
    { "name": "RHip", "x": 0.47, "y": 0.63, "c": 0.89 },
    ...
  ]
}
```

- `frame` — номер кадра в нормализованном видео (целое число).
- `ts` — временная отметка в секундах от начала видео (плавающее число). Используется для синхронизации с проигрывателем.
- `person_id` — идентификатор человека (в MVP всегда `0`). Заложено на будущее, если понадобится поддержка нескольких спортсменов.
- `kp` — массив ключевых точек. Имя, порядок и количество точек определяются контрактом модели (`pose_contract_v1.json`).
  - `name` — название сустава (например, `LHip` — левое бедро).
  - `x`, `y` — координаты в нормализованных единицах [0 .. 1], где `(0,0)` — левый верхний угол, `(1,1)` — правый нижний.
  - `c` — confidence (достоверность) в диапазоне [0 .. 1].

### Версионирование

Версия файла указывается в названии: `keypoints_v1.jsonl`. При изменении порядка суставов, добавлении новых точек или форматировании будет выпущена новая версия (например, `v2`).

## 2. Вычисленные фичи — `features_v1.json`

Файл содержит агрегированные метрики по всему видео и временные ряды по кадрам/времени. Структура определена схемой `features_v1.jsonschema`.

### Пример

```json
{
  "schema_version": "v1",
  "fps": 30,
  "segments": [
    {
      "t0": 1.0,
      "t1": 6.5,
      "stats": {
        "knee_flex_mean_deg": 125.3,
        "torso_lean_max_deg": 32.7
      }
    }
  ],
  "timeseries": {
    "t": [0.0, 0.033, 0.066, ...],
    "knee_left_deg": [150.0, 148.7, 149.2, ...],
    "knee_right_deg": [151.2, 149.8, 150.4, ...],
    "torso_lean_deg": [12.3, 13.1, 14.0, ...]
  }
}
```

#### Поля

- `schema_version` — версия схемы (`v1`).
- `fps` — частота кадров нормализованного видео.
- `segments` — список сегментов, выделенных для анализа (для MVP это может быть весь ролик или отдельные дуги). Каждому сегменту соответствует статистика (`stats`) — средние/максимальные значения метрик.
- `timeseries` — временные ряды, где `t` — массив временных отметок, а остальные ключи соответствуют измеряемым метрикам.

### Изменение схемы

Если появятся новые метрики или формат представления изменится, будет выпущена новая версия (например, `features_v2.json`), а актуальная схема будет обновлена в `schemas/features_v2.jsonschema`.

## 3. Фидбек — `feedback_v1.json`

Файл содержит результат применения rule‑based правил. Каждое правило может генерировать один или несколько пунктов фидбека. Структура определена схемой `feedback_v1.jsonschema`.

### Пример

```json
{
  "ruleset_version": "v1",
  "items": [
    {
      "severity": "warn",
      "title": "Слишком прямые колени",
      "detail": "На дуге колени разгибаются > 160° чаще 40% времени",
      "metric": "knee_flex_deg",
      "t_ranges": [[2.1, 3.4], [4.0, 4.2]]
    },
    {
      "severity": "info",
      "title": "Хороший наклон корпуса",
      "detail": "Средний наклон корпуса в пределах 20–30°.",
      "metric": "torso_lean_deg",
      "t_ranges": []
    }
  ]
}
```

#### Поля

- `ruleset_version` — версия набора правил (`v1`).
- `items` — массив пунктов фидбека.
  - `severity` — важность: `info`, `warn`, `error` (в MVP достаточно `info` и `warn`).
  - `title` — краткое описание проблемы/совета.
  - `detail` — детальная формулировка, которая отображается пользователю.
  - `metric` — имя метрики, на которой основано правило.
  - `t_ranges` — список временных диапазонов, где правило нарушается (в секундах). Пустой список означает, что правило относится ко всему сегменту.

### Версионирование

Новое правило или изменение порога приводит к увеличению `ruleset_version`. При появлении ML‑моделей для рекомендаций формат может быть расширен полями `score`, `confidence` и др.

## 4. Коды версий

Для всех артефактов используется следующая нотация версий:

- `v1` — версия MVP, описанная в этом документе.
- `v2`, `v3`, … — новые версии, обратно совместимые или нет. При несовместимом изменении всегда увеличивается номер версии файла.

## Заключение

Чётко определённые форматы данных и версионирование позволяют разработчикам и исследователям работать с артефактами, не опасаясь неожиданных изменений. JSON и JSONL легко читаются на разных языках и хорошо подходят для прототипа. При переходе к большим объёмам данных возможно использование более эффективных бинарных форматов (например, Parquet), однако изначальные форматы остаются полезны для дебага и открытого API.
