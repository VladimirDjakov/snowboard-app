# ADR 002: Формат JSONL для keypoints

- **Статус:** Принято
- **Дата:** 2026‑01‑08

## Контекст

После инференса модели pose estimation необходимо сохранить координаты ключевых точек для каждого кадра видео. Точки должны быть доступны воркерам для дальнейших этапов (вычисление фич, визуализация) и потенциально для сторонних клиентов/исследователей. Важно обеспечить возможность писать файл по мере поступления данных, не держа всё в памяти.


## Решение

Формат хранения выбран в виде **JSONL (JSON Lines)**. Каждый кадр — отдельная строка, представляющая объект JSON с полями `frame`, `timestamp`, `person_id` и `keypoints`. Данные записываются построчно, поэтому можно обновлять файл инкрементально.

### Аргументы в пользу JSONL

1. **Простота записи.** Воркеры могут записывать строки по мере обработки батчей кадров, не храня в памяти полный массив. При сбое можно продолжить запись с последнего успешного кадра.
2. **Удобство чтения.** Формат легко читается стандартными библиотеками JSON. Его можно стримить и парсить по строкам.
3. **Гибкость.** Легко добавить новые поля без изменения существующих строк. Каждая строка независима.
4. **Читаемость.** Формат человекочитаемый, что упрощает дебаг.

## Альтернативы рассмотрены

- **Parquet / Avro / Protocol Buffers.** Бинарные форматы эффективнее по размеру и скорости, но сложнее для быстрой итерации и дебага. Они требуют схемы и дополнительных зависимостей. На этапе MVP эта сложность неоправданна. В перспективе для больших объёмов данных может быть добавлена экспорт/импорт в Parquet.
- **Один большой JSON-массив.** Такой файл приходится держать в памяти для сериализации и сложно добавлять элементы без перезаписи всего файла.
- **CSV.** CSV не подходит для вложенных структур данных (массив ключевых точек) и требует искусственной сериализации.

## Последствия

- **Плюсы.** Лёгкая имплементация, гибкость и читабельность. Поддержка различными инструментами (python, node.js, Go и др.).
- **Минусы.** Более крупный размер по сравнению с бинарными форматами. Требует постобработки для агрегации и анализа (файл строк). Неподходит для прямого чтения массивами без постобработки.

Вывод: JSONL оптимально подходит для MVP. В будущем можно реализовать экспорт в Parquet для работы с датасетами и машинным обучением.
