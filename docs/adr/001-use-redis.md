# ADR 001: Использование Redis как брокера задач

- **Статус:** Принято
- **Дата:** 2026‑01‑08

## Контекст

В MVP необходимо реализовать асинхронный пайплайн обработки видео: после загрузки ролика нужно выполнить несколько независимых стадий (normalize, pose tracking, feature extraction, rule-based feedback) на разных типах ресурсов. Требуется простая очередь задач, поддерживающая задержки между этапами и ретраи при сбоях. Важно быстро запуститься без сложной настройки кластера.

## Решение

Для обработки задач выбран Redis — популярное in‑memory хранилище данных, поддерживающее списки и структуры данных, на основе которых реализуются библиотеки очередей (RQ). Используется связка `Redis + RQ`: API кладёт задачи в список, воркеры извлекают их и выполняют. Каждая стадия имеет отдельную очередь (`cpu` и `gpu`), что позволяет контролировать количество воркеров и приоритеты.

### Аргументы в пользу Redis

1. **Простота.** Redis легко поднять локально и в облаке. Для MVP не требуется сложная настройка или оркестрация.
2. **Лёгкий переход в продакшен.** Можно быстро переключиться на управляемый Redis (AWS ElastiCache/GCP MemoryStore). Для высокой нагрузки есть решения с персистентностью.
3. **Поддержка очередей.** Библиотека RQ предоставляет готовый API для работы с Redis как с очередью задач, включая ретраи и dead letter queue (DLQ).
4. **Наблюдаемость.** Очередь в Redis легко мониторить: можно посмотреть длину, потребителей, failed jobs.

## Альтернативы рассмотрены

- **RabbitMQ/Kafka.** Эти брокеры предоставляют более надёжные гарантии доставки и гибкие возможности (routing, topics), но требуют дополнительной инфраструктуры, настройки и поддержки. Для MVP это избыточно. В перспективе возможен переход на RabbitMQ или Kafka для масштабирования.

> **Детальное сравнение:** См. [ADR 001b: Детальное сравнение брокеров очередей](001b-queue-broker-comparison.md) для подробного анализа Redis, RabbitMQ и Kafka с рекомендациями по выбору.
- **PostgreSQL LISTEN/NOTIFY.** Можно использовать триггеры и уведомления для запуска обработки, но это усложняет схему БД и даёт менее гибкие возможности для ретраев.

## Последствия

- **Производительность.** Redis работает в памяти и обеспечивает низкую задержку обработки, что подходит для небольшого числа задач.
- **Надёжность.** Redis без персистентности может потерять данные при краше узла. Для продакшена потребуется репликация и сохранение снимков (RDB/AOF).
- **Сложность миграции.** Переход на RabbitMQ/Kafka потребует переписывания кода очередей, но будет легче благодаря явному разделению логики постановки задач и обработки в текущем дизайне.
